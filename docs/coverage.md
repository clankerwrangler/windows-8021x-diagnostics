# Coverage and troubleshooting matrix

Use this matrix to separate an endpoint observation from its possible cause. It is a troubleshooting guide, not a claim that the script automates every row. Read the collection status and finding limitations in each report. A missing collector or untested scenario remains unknown.

## Diagnostic coverage

See the [test results](../tests/test-results.md) for Windows PowerShell 5.1 validation on Windows 11, including revision-specific synthetic and limited read-only collection coverage. Those tests do not establish successful wired profile retrieval, connected-WLAN queries, real EAP authentication, or RADIUS interoperability. A collector's presence does not guarantee that it succeeds on every endpoint.

| Status | Current coverage | Important limits |
| --- | --- | --- |
| **Automatic collection** | Interface/link and driver metadata; IPv4/IPv6 addresses, configured DNS, and default gateways; selected Windows service state. | No radio switch/airplane-mode assessment, complete routing/NRPT analysis, DNS query, ping, DHCP renewal, or active application probe. |
| **Automatic collection** | Native WLAN current-connection metadata and bounded profile summaries; per-interface wired profile summaries through supported `netsh lan export profile`. | Current WLAN queries can be denied. Wired export uses sensitive temporary XML and does not prove authorization. An unnamed LAN profile uses the interface alias. GPO flags and exported settings do not resolve MDM assignment or all effective policy. |
| **Automatic collection** | Selected OneX/profile settings, namespace-scoped EAP type/depth, phase-2 method names, validation settings, server names, root-pin fields, Windows-logon-credential settings, SSO type, and timers. | This is not a full EAP schema/selector implementation. Validation is an aggregate of explicit method settings, not a per-method effective verdict. Method-specific defaults, pin matching, and vendor extensions still need review. |
| **Automatic collection** | CurrentUser and LocalMachine personal-certificate metadata: thumbprint, validity, EKU, private-key-presence flag, and cache-only Crypt32 chain status. | No root-store inventory, certificate subject/SAN, actual private-key operation, issuer-filter evaluation, selected-certificate proof, live revocation, or RADIUS server-certificate validation. |
| **Automatic collection** | Bounded WLAN/Wired AutoConfig, EapHost, Schannel, CAPI2, and NTLM history, with availability, unsupported provider/channel pairing, and truncation status. | `UnsupportedProviderChannel` is not empty history; supported pairings remain queried. Channels can also be missing, disabled, or denied. Documented ONEX reasons and a small HRESULT set are named on historical failure findings; other codes stay numeric. Rendered messages are opt-in. Events remain historical and can be uncorrelated. |
| **Automatic findings** | Partial/empty evidence; missing target alias; target-only disabled/disconnected/not-present adapter; requested profile not observed with complete versus incomplete visibility; required-profile or targeted-medium service state. | A missing query result is not global absence. A targeted stopped service is a relevance clue when no enterprise profile was observed; an unused adapter or service is not automatically a fault. |
| **Automatic findings** | Explicit disabled validation in at least one EAP method; missing structural EAP-TLS candidates with scoped date/key/EKU counts; candidate cached-chain details; and near expiry. | A stored profile need not be the attempted profile. Unrelated certificates are not defects. Candidate metadata and cached-chain errors do not prove selection, key use, server chain acceptance, mapping, or current revocation. |
| **Automatic findings** | Provider-qualified historical authentication failures, including documented ONEX and selected certificate/TLS HRESULT names; supporting EAP/TLS/NTLM history; unavailable current-WLAN query; up-interface address/DNS configuration warnings; explicit end-to-end uncertainty. | No live authentication success verdict, complete reason-code catalog, effective Credential Guard check, or root/server-name match verdict. Named HRESULTs are endpoint codes, not RADIUS policy. |
| **Manual endpoint review** | Radio/link intent, detailed method/inner-method/SSO policy, effective Credential Guard and Windows compatibility, GPO/MDM configuration source, certificate selection/key/provider/context, trust pins, time, full IP/DNS/routing, and controlled reproduction. | The runbook describes these checks; it does not mean the script collected or evaluated them. Some require collection in the affected user context or deeper native evidence. |
| **Not observable from this snapshot** | RADIUS/NPS decision and matched policy; NAS shared-secret/path; DC strong mapping; server trust/revocation; NAC posture; applied VLAN/role/ACL; CoA/reauthentication session handling; complete EAP handshake. | Correlate the endpoint evidence with server and network logs. Endpoint symptoms indicate a possible stage, not the infrastructure verdict. |

Reports use `High`, `Medium`, and `Low` confidence labels. These qualify the finding's scoped evidence; they do not replace the endpoint-proven/indicated/server-only distinction in this guide. The three report artifacts are text/JSON, not HTML. The detailed evidence is in `evidence.json`; the pipeline and report object contain findings and collection status.

## Evidence and scope

Use these evidence classes when interpreting a report:

- **Endpoint-proven**: A local fact was observed in a named source and context at a recorded time. For example, an adapter is disabled, a profile selects EAP-TLS, or a certificate is expired relative to the endpoint clock. This class does not prove why the authentication server rejected an attempt.
- **Indicated**: Local facts support a possible cause, but another explanation or unobserved context remains. For example, a certificate might be unsuitable, or an old failure might relate to a prior attempt.
- **Server-only**: The decision requires evidence from the switch, access point (AP), RADIUS server, network access control (NAC) service, certification authority, or domain controller. An endpoint can provide a correlation key, not that decision.

Keep time separate from confidence. Record the capture time, event time, time zone, lookback window, and whether a finding concerns the current link or historical activity. A historical failure remains useful after success but does not establish the present connection state. Correlate by interface GUID or other stable interface identity, profile or SSID, and the attempt time. An interface name alone can change. An uncorrelated event does not establish a fault on a particular adapter.

Retain the provider, channel, event ID, event version, and structured event data. A numeric reason code is meaningful only in its documented namespace. WLAN, EAP, Win32, HRESULT, Schannel, and NPS codes are not interchangeable. Keep the original numeric value, including hexadecimal when available. Localized rendered text is supporting evidence, not a language-independent detection contract. Unknown codes remain unknown; a substring such as `password` is not a definitive diagnosis.

Use provider-qualified event mappings: WLAN AutoConfig `12012`/`12013` identify authentication success/failure, as do Wired AutoConfig `15505`/`15514`. Wired `15501`/`15502` describe adapter connection/profile application, not authentication outcomes. Keep the provider, event version, and Windows build with the evidence.

A successful collection with no matching events is different from an unsupported provider/channel pairing, a disabled channel, denied access, a missing channel, truncation, a timeout, or an unattempted collector. Report those states separately. Enabling logging, location permission, tracing, or services changes the environment; this script reports the gap without changing those settings.

## Native reason-code interpretation

Interpret a code only when its provider, event version, and field contract establish the namespace. A value that matches a documented constant does not establish that contract. Keep unverified event fields unmapped. The following table is a reference for confirmed `ONEX_REASON_CODE` values, not a claim that every AutoConfig numeric field uses this namespace. See the diagnostic coverage section for automatic coverage.

| Confirmed ONEX value | Meaning | Conditional next step |
| --- | --- | --- |
| `327681` (`0x00050001`), `ONEX_UNABLE_TO_IDENTIFY_USER` | The module could not identify a usable credential set. | Compare the historical sign-in state with the intended user, machine, and SSO flow. Check the correct identity and certificate-store context; this code alone does not establish a bad password. |
| `327683`, `327684`, `327700` (`0x00050003`, `0x00050004`, `0x00050014`), UI disabled, failed, or not permitted | Required user input could not be obtained or was not permitted. Exact behavior depends on the Windows version. | Check interactive versus pre-logon/machine authentication and the user/machine scope of saved profile data. Correct profile or deployment mismatches. Accepting an unverified server can expose credentials. |
| `327686`, `327687` (`0x00050006`, `0x00050007`), authenticator absent or no response to identity | The peer disappeared or did not respond, or the endpoint received no response to its identity response. | Check link, range, and roaming history. Correlate switch/AP and RADIUS logs for the same attempt. This does not identify a failed server, blocked port, or bad shared secret. |
| `327688`, `327690`, `327691`, `327695`, `327696` (`0x00050008`, `0x0005000A`, `0x0005000B`, `0x0005000F`, `0x00050010`) | Unsupported profile version, disallowed EAP type, invalid EAP type/flags, invalid authentication mode, or invalid EAP connection properties, respectively. | Compare the effective profile with the Windows build and medium. Repair the deployed GPO/MDM profile. Bulk profile deletion or global TLS changes affect more than the failed profile. |
| `327685` (`0x00050005`), `ONEX_EAP_FAILURE_RECEIVED` | The EAP module returned an error. | Retain any separately documented EAP error details and correlate the attempt. This code alone does not prove a RADIUS rejection, bad password, or certificate defect. |

The inbox `WlanReasonCodeToString` API supplies display text for a confirmed `WLAN_REASON_CODE`, including its documented ONEX reasons. The caller provides a fixed WCHAR buffer and a null reserved pointer. Keep the original numeric code and decoder status. Localized descriptions are not stable rule identifiers. `EapErrorCode`, vendor, HRESULT, and NPS values require their own documented namespace and decoder; their numeric values are not interchangeable with WLAN reasons.

## Link, radio, driver, and service checks

| Failure mode | Evidence and limit | Next checks and remediation |
| --- | --- | --- |
| Ethernet adapter is disabled or media is disconnected | **Endpoint-proven** for the captured local state. It does not distinguish cable, dock, transceiver, switch power, or switch configuration. | Check the cable, dock, switch port, and intended adapter state. Reconnecting or enabling an adapter can interrupt access. |
| Wi-Fi radio is off, airplane mode is active, or no WLAN interface is visible | **Endpoint-proven** only for an available native state. A denied API call is not an absent radio. | Check hardware and software radio controls and the device's intended use. Radio changes can interrupt current connections. |
| Windows denies Wi-Fi queries because of location or application permission | **Endpoint-proven** collection limitation, not proof of a missing adapter, profile, or SSID. Behavior depends on the Windows build and API. | Check Windows location and application permissions. Granting access changes the application's ability to read Wi-Fi details; denial remains a collection limitation. |
| SSID cannot be found, association fails, or signal is weak | **Indicated** from available scan/interface evidence and correlated WLAN events. Hidden SSIDs, coverage, channel rules, radio compatibility, and AP faults can look similar. | Compare the intended SSID and security mode with the AP configuration. Check coverage and AP events. Avoid repeated scans or forced reconnects during an active session. |
| Driver or firmware cannot support the configured security mode | Version, hardware ID, and native capability output are **endpoint-proven**; a causal driver defect is usually **indicated**. An old date alone is not a defect. | Compare the exact hardware, driver, OS build, cipher, and authentication mode with vendor support. Check hardware- and build-specific driver or firmware updates. |
| `WlanSvc` is unavailable for Wi-Fi or `dot3svc` is unavailable for wired 802.1X | Service state is **endpoint-proven**. A stopped service on an unused medium is not a failure of the active medium. | Check intended adapter use and service configuration. Restore the service configuration needed by the target medium. |
| `EapHost` is stopped | Service state is **endpoint-proven**; a stopped demand-start service alone does not prove failure. | Correlate startup errors, events, trigger/start configuration, and an actual authentication attempt. |
| A virtual, VPN, Bluetooth, loopback, or disconnected adapter appears unhealthy | Adapter presence is **endpoint-proven**, but it might be unrelated to the target access link. | Identify the target physical interface and retain other adapters as context. A disconnected, unrelated adapter does not establish an 802.1X failure. |
| Authentication worked before sleep, roaming, docking, or an OS update | History is **indicated** unless the transition and failure correlate on the same interface. | Compare driver/power events, AP or switch logs, reauthentication timing, and the last known good build. Preserve evidence before a controlled reproduction. |

## Profiles, methods, credentials, and policy

| Failure mode | Evidence and limit | Next checks and remediation |
| --- | --- | --- |
| Required wired or enterprise Wi-Fi profile is missing | **Endpoint-proven** only within the enumerated interface and user/policy scope. A failed export or denied query is not absence. | Deploy the intended profile through GPO, MDM, or local configuration in the correct scope. Bulk deletion can remove unrelated network settings. |
| Profile name, SSID, interface, or security mode does not match the intended network | Local profile values are **endpoint-proven**; intended infrastructure configuration is external. A profile name need not equal its SSID. | Compare the exact deployed XML and infrastructure settings. Correct the mismatch at its configuration source: GPO, MDM, or local settings. |
| 802.1X is disabled or not enforced where required | The observed profile setting is **endpoint-proven**. Whether the network requires 802.1X is external. | Confirm the access design and deploy the matching configuration. Enabling enforcement on an active link can interrupt access. |
| GPO and MDM profiles conflict, policy has not applied, or a local edit is overwritten | Profile source and available policy evidence are local facts; the winning policy and assignment might remain **indicated**. | Compare computer and user policy scope, MDM assignment, synchronization time, and policy events. Fix the authoritative policy, not a local copy that management replaces. |
| Machine authentication is required, but the profile selects user authentication, or the reverse | Parsed authentication mode is **endpoint-proven**. The identity used in a specific attempt needs correlated evidence. | Align the intended identity with pre-logon access and RADIUS policy. XML `authMode` uses `machineOrUser`, `machine`, `user`, or `guest`; the corresponding `netsh` parameters use `machineOrUser`, `machineOnly`, `userOnly`, or `guest`. Check both stages when access changes at sign-in. |
| Pre-logon, post-logon, or single sign-on (SSO) behavior is wrong | SSO settings are local facts; timing and interactive requirements are **indicated**. | Check profile SSO timing, domain reachability, credential prompts, and machine-to-user transitions. Coordinate changes to preserve pre-logon access. |
| PEAP with EAP-MSCHAPv2 cannot use sign-in credentials | The outer and inner methods, SSO settings, and observed Credential Guard state are local facts. They indicate compatibility risk, not a proven wrong password. | Check the configured credential flow and the authentication server's reason. Certificate-based authentication can avoid the incompatible SSO flow. Disabling Credential Guard removes credential-isolation protection. |
| Automatic retries stop after a failure | Block-period, held-period, and maximum-failure settings are local facts. A blocked retry is **indicated** unless the attempt timeline confirms it. | Check effective timers and failure counts, then retest after correcting the cause. Repeated authentication attempts can trigger account lockout and obscure the attempt timeline. |
| Password, account state, realm, or user identity is rejected | A client rejection event can be **indicated**. Lockout, expiration, group membership, account mapping, and exact policy denial are **server-only**. | Correlate the attempt with identity and RADIUS logs. Repeated password attempts can cause lockout; raw passwords and cached credentials are not needed for event correlation. |
| PEAP is mistaken for a password-only method | PEAP is a protected outer method; the inner method determines whether credentials or a client certificate are required. | Inspect outer and inner EAP configuration. Treat PEAP-EAP-TLS differently from PEAP-EAP-MSCHAPv2. |
| PEAP cryptobinding or outer-identity routing does not match the server | Local cryptobinding and identity-privacy settings are facts; the server negotiation and proxy route are external. An anonymous outer identity is not the authenticated inner user. | Compare client and server cryptobinding support, outer realm routing, and inner authentication. Disabling binding or identity privacy removes those protections rather than resolving the mismatch. |
| EAP-TLS has no apparently suitable client certificate | Inventory findings are **indicated** unless the actual selection and handshake are observed. | Use the certificate checks in the next section. Confirm the intended user or machine identity, enrollment, and server policy. |
| TEAP chaining fails | A profile can show TEAP and inner methods. Whether machine and user authentication both satisfied the server's chaining policy is **server-only**. | Check both identities, the order and choice of inner methods, Windows support, and the RADIUS server's TEAP/chaining configuration. Windows NPS and Windows clients support different sets of EAP methods. |
| EAP-TTLS fails | TTLS is a protected outer method. Its inner authentication can use EAP or a non-EAP method, so an EAP type list alone can miss phase 2. | Inspect the configured phase-2 method and realm as well as the outer TLS settings. Verify the server's supported TTLS flow. |
| An EAP type or vendor extension is unknown to the parser | **Endpoint-proven** parser limitation. Unknown does not mean unsupported by the installed client or server. | Preserve safe type/vendor identifiers and report the unparsed configuration. Use the profile and provider documentation to identify the unparsed configuration. |
| MAC randomization, a replaced dock, or an adapter change alters NAC identity | Observed MAC/configuration changes are **indicated**. NAC endpoint registration and policy are **server-only**. | Compare the calling-station identity with NAC records and per-network MAC settings. Global randomization changes affect other networks and tracking privacy. |

In Windows EAP profiles, common type identifiers are EAP-TLS `13`, EAP-TTLS `21`, PEAP `25`, EAP-MSCHAPv2 `26`, and TEAP `55`. Record where each value appears in the profile. A number nested in a filter, an inner method, or unrelated XML is not automatically the selected outer method. Keep namespace and vendor information when applicable.

Native client support is not the same as RADIUS server support. Microsoft's current EAP overview documents EAP-TTLS client support beginning with Windows 8 and TEAP client support beginning with Windows 10 version 2004 (build 19041). It states that NPS does not support EAP-TTLS or TEAP. Windows supports EAP-TLS and EAP-MSCHAPv2 as PEAP and TEAP inner methods. Recheck this guidance for the actual client/server release before diagnosing an unsupported combination.

## Certificate selection, trust, and mapping

| Failure mode | Evidence and limit | Next checks and remediation |
| --- | --- | --- |
| Certificate is in the wrong store or identity context | Store location is **endpoint-proven**. `CurrentUser` is the account running the collector, not every signed-in user. `Cert:\LocalMachine\My` and `Cert:\CurrentUser\My` are separate contexts. | Match the certificate to user or machine authentication. For user authentication, collect metadata in the affected user's session; another account's store can show different certificates and key access. |
| Certificate is expired or not yet valid | Dates are **endpoint-proven** relative to the endpoint clock. A bad clock can invalidate that conclusion about real time. | Verify trusted time, then renew or enroll through CA/MDM. Removing the old certificate before the replacement is deployed can break existing authentication. |
| Certificate has no associated private key | `HasPrivateKey = false` is an observed property for that certificate. Other certificates or hardware credentials might still be valid. | Check enrollment and the intended key provider. Re-enroll the affected identity if its key is missing. The report needs certificate metadata, not private-key material. |
| A private key exists but is inaccessible or requires a smart card/PIN | `HasPrivateKey = true` does not prove the supplicant can open or use the key. Provider, ACL, hardware, PIN, and service context can differ. | Check key-provider events, enrollment, and ACLs in the actual user/service context. Broader key permissions expose the key to additional principals; a PIN is not needed in the report. |
| EKU or key usage does not meet policy | Parsed EKU/key usage is local metadata; actual acceptance depends on method, platform, template, and server policy. Missing EKU is not universally equivalent to a wrong EKU. | Check Client Authentication OID `1.3.6.1.5.5.7.3.2` for client certificates and Server Authentication OID `1.3.6.1.5.5.7.3.1` for server certificates, plus relevant key usage. Reissue with a template matching the required certificate purposes. |
| SAN, subject, UPN, DNS identity, or certificate mapping does not match the account | Certificate names are local metadata. Account matching, SID/strong mapping requirements, and policy acceptance are **server-only**. | Compare certificate identity, account, mapping rules, and domain-controller events. A matching display name or subject CN does not establish valid mapping. |
| A previously accepted certificate fails after domain-controller hardening | The date correlation is **indicated**. Strong certificate mapping enforcement is **server-only** and depends on server updates and configuration. | Check Microsoft KB5014754 in the official references and correlate DC/NPS events. Correct issuance or explicit strong mapping. Restoring weak mapping or rolling back hardening removes the protection introduced by those updates. |
| No certificate matches an issuer or EKU selection filter | Profile filter values and enumerated metadata are local facts. The script does not implement the full Windows certificate selector. | Compare the intended certificate and every relevant filter, including issuer restrictions. Label candidates as candidates, not as the certificate actually selected. |
| Several candidate certificates exist | Candidate count is **endpoint-proven** for the observed stores. It does not prove which certificate Windows selected. | Correlate the selected thumbprint in available EAP/CAPI events or a controlled reproduction. Correct the specific enrollment/filter issue. Deleting all certificates can break unrelated identities. |
| Intermediate or root trust is missing or the chain is incomplete | Local store presence is **endpoint-proven**. A chain failure in the collector context is **indicated** for the supplicant. A root's presence alone does not prove a valid chain. | Install the intended roots/intermediates in the correct store and check the presented chain and server-side trust. Adding a trust anchor changes which certificates are accepted. |
| A trusted-root pin uses a different hash or configuration element | Profile pins and available certificate hashes are local facts. A comparison with the wrong hash cannot prove that a root is absent. | TLS/PEAP use `TrustedRootCA`; TTLS/TEAP use `TrustedRootCAHashes`. Microsoft documents SHA-1 for these pins except TEAP, which uses SHA-256. Match the correct algorithm and keep issuer-selection pins separate from server-trust pins. |
| Server certificate name does not match the configured RADIUS server names | Profile name restrictions are local facts. The certificate actually presented during an attempt might not be observable in the snapshot. | Compare configured server names, the presented certificate, trusted anchors, and load-balanced RADIUS nodes. Renew or correct the configured profile or server certificate. |
| Server validation, trusted-root selection, or name restrictions are unsafe or inconsistent | Parsed settings are **endpoint-proven**, but omitted settings can have method/version-specific defaults. A missing XML element is not automatically `false`. | Compare effective method-specific settings with the intended trust anchors and server names. Disabled validation or accepting any server removes server-identity checking. |
| Revocation status is unknown, stale, or cannot be retrieved | Cached/offline chain results do not prove that a certificate is currently unrevoked. An unavailable CRL/OCSP endpoint differs from a revoked result. | Verify revocation evidence in the actual validation context. Check configured CRL/OCSP and AIA availability, including pre-auth access. Disabling revocation checking removes the check for revoked certificates. |
| Client certificate looks valid locally, but RADIUS rejects it | **Indicated** at the endpoint. The server validates the client chain, revocation, identity mapping, policy, and possibly device state independently. | Correlate the exact rejection, selected client certificate, server trust chain, and mapping outcome in RADIUS/PKI evidence. |
| Server certificate looks valid in a browser, but EAP fails | Browser HTTPS and EAP can use different names, chains, stores, TLS behavior, and contexts. The browser result is not an EAP proof. | Validate the actual EAP server certificate and profile rules in the relevant context. |

The script assesses certificate chains with Windows Crypt32 using cached data only. It does not test private-key use, full Windows certificate selection, the live RADIUS server certificate, or current online revocation. Keep the store/engine context and cache limits with the result. Online validation can retrieve AIA, CRL, or OCSP data and alter caches. For further validation, account for network effects, identity context, timeout, and revocation mode.

When an Active Directory KDC participates in certificate authentication, strong mapping is a server-side requirement. KB5014754 records the move to default enforcement with the 2025-02-11 updates and the end of the compatibility registry option with the 2025-09-09 updates. Correlate the applicable `Kdcsvc` events and mapping configuration on the domain controller. A missing SID extension alone does not prove rejection because supported explicit strong mappings can also satisfy the requirement. The endpoint build does not establish a DC's patch or enforcement state.

## Windows version, method, and TLS compatibility

| Failure mode | Evidence and limit | Next checks and remediation |
| --- | --- | --- |
| Credential Guard changes SSO behavior after an upgrade | OS build and observed running/configured state are local facts. Registry intent alone does not prove Credential Guard is running. | Check the effective state and Microsoft compatibility guidance. Test the intended credential flow and evaluate certificate-based alternatives to incompatible MSCHAPv2 SSO. |
| A method is absent on the installed Windows release | Build and locally observed method registration are local facts. Product/version documentation determines built-in support. | Check client and server support separately. Built-in methods vary by Windows release; this script does not require a third-party supplicant. |
| TLS protocol, cipher, signature, or key requirements differ between client and RADIUS | OS build, configured controls, and correlated EAP/Schannel events are **indicated**. The negotiated or rejected handshake requires deeper evidence. | Compare both sides' supported protocols and the presented chain. Patch or reconfigure the incompatible server. Globally enabling legacy protocols affects other applications and weakens their protocol protections. |
| WPA3-Enterprise 192-bit requirements are not met | Profile/security mode and certificate metadata are local facts. Generic TLS support or a Client Authentication EKU is insufficient for this mode. | Check EAP-TLS, required certificate/key parameters and cipher suites, OS, driver, AP, and RADIUS support. Downgrading the security mode changes its requirements rather than demonstrating 192-bit support. |
| An OS upgrade tightens server certificate validation | A before/after correlation is **indicated**, not proof of a Windows defect. | Compare effective server-name, root, EKU, chain, and method configuration against guidance for that Windows build. Fix the trust/profile inconsistency instead of disabling validation. |
| Local time or time synchronization is wrong | Endpoint time and service/status metadata are local facts. They do not independently establish correct UTC. | Compare with the organization's trusted time source and repair time synchronization. Recheck certificate validity and domain authentication afterward. |
| A security product, third-party EAP provider, or local policy affects the attempt | Observed registration, policy, or events are **indicated** unless a specific block is recorded. | Correlate the attempt with the specific security product, provider, or filter logs. Disabling firewalls or endpoint protection affects more than EAP and increases exposure. |

Microsoft's Windows 11 EAP change guidance describes these version-sensitive checks:

- Windows 11 can trust a server through a stored server-certificate thumbprint, or through the documented chain/root-profile requirements and enabled server-name validation. A missing root pin alone does not prove failure if another supported trust path applies. A root in the wrong authentication context is not sufficient.
- Windows 11 version 21H2 (build 22000) matches server names case-sensitively. Version 22H2 (build 22621) restores case-insensitive matching. Compare the actual configured name and certificate rather than assuming a case-only difference is harmless on every build.
- Windows 11 uses TLS 1.3 for EAP-TLS. Version 22H2 also changes PEAP and EAP-TTLS to use TLS 1.3 by default. The change document lists NPS and older third-party server limitations. Verify the actual client/server support and negotiation; differing maximum TLS versions alone do not establish failure.
- User acceptance, stored trust, and WPA3-Enterprise Trust Override Disable certificate policies can affect prompting. A missing prompt does not prove that credentials were never requested. Accepting an unverified server bypasses server-identity validation.

## RADIUS, NAC, VLAN, and dynamic authorization

The Windows supplicant normally exchanges EAP over LAN (EAPOL) with a switch or AP. That authenticator exchanges RADIUS with its server. A port test from the endpoint does not test the authenticator-to-RADIUS path. `Test-NetConnection -Port` tests TCP, not ordinary UDP RADIUS. An endpoint TCP failure on port 1812 does not establish a RADIUS outage.

| Failure mode | Evidence and limit | Next checks and remediation |
| --- | --- | --- |
| EAPOL never reaches or is not handled by the switch/AP | The endpoint can indicate a timeout or lack of response, but packet delivery and controlled-port state need infrastructure evidence. | Check the exact switch port/AP client, 802.1X configuration, supplicant/authenticator exchange, and physical path. |
| RADIUS server is unreachable, uses the wrong shared secret, or rejects the NAS client | **Server-only**. Similar endpoint timeouts can result from several faults. | Check authenticator and RADIUS logs, NAS registration, transport, shared-secret consistency, and applicable firewall rules. Including the shared secret in a report exposes that credential. |
| NPS accepts or rejects the attempt | **Server-only** for the NPS verdict. A local failure event is not NPS event 6273. | Correlate NPS Security events 6272 (accepted) and 6273 (rejected), when auditing is configured, using time and client/NAS identity. Read the policy and native reason code. |
| RADIUS proxy, connection request policy, network policy, group, or realm is wrong | **Server-only**, with local identity/profile hints. | Check request routing, matched policies, authentication method, account lookup, and group conditions on the responsible servers. |
| NAC posture, device registration, certificate status, or compliance fails | **Server-only**. A quarantine-like address range merely indicates a possibility. | Inspect NAC/MDM endpoint identity, posture results, policy, and remediation requirements. Exempting a device from posture checks changes access policy without resolving its posture failure. |
| RADIUS assigns a dynamic VLAN, role, filter, or ACL that the authenticator cannot apply | **Server-only**. An endpoint address does not prove the assigned VLAN or authorization attributes. | Compare Access-Accept attributes with switch/AP configuration, VLAN availability, trunking, role/ACL support, and DHCP reachability. |
| Authentication succeeds, but the endpoint gets the wrong subnet | Address and routes are **endpoint-proven**; incorrect VLAN assignment is **indicated** at most. Static addressing, a stale lease, VPN routes, and multiple interfaces can also explain it. | Confirm the intended access policy and actual authenticator assignment before changing endpoint IP settings. |
| RADIUS Change of Authorization (CoA), disconnect, reauthentication, or session timeout fails | **Server-only** for send/receive, ACK/NAK, session lookup, and policy. The endpoint can show a correlated link transition. | Correlate RADIUS/NAC and authenticator session identifiers, authorization changes, timers, and dynamic-authorization logs. Check the infrastructure path, not an endpoint CoA port. |
| Machine authentication succeeds, then user authentication changes or loses access | Endpoint history can **indicate** the transition. Applied VLAN/role and authorization are **server-only**. | Compare both authentications and the intended machine/user policy. Check lease/route behavior after a VLAN transition. |
| Large certificate chains or EAP fragmentation fail through an AP, switch, proxy, or server | Repeated handshake/timeouts are **indicated**. Packet size, EAP fragmentation, and RADIUS proxy behavior need infrastructure or controlled trace evidence. | Compare the affected chain size, device firmware, RADIUS/proxy behavior, and a known-good path. Reducing certificate strength or TLS security changes security properties rather than measuring fragmentation. |

## Post-authentication IP and DNS

| Failure mode | Evidence and limit | Next checks and remediation |
| --- | --- | --- |
| Interface is connected, but 802.1X authorization is unknown | Media/link state is **endpoint-proven**, not proof of 802.1X success or unrestricted access. | Correlate an authentication event and infrastructure authorization before attributing IP failures to RADIUS. |
| IPv4 APIPA (`169.254.0.0/16`) or no expected DHCP lease appears | Address metadata is **endpoint-proven**; DHCP/authorization failure is **indicated**. Usable IPv6 might still provide access. | Check intended IPv4/IPv6 design, DHCP client events, authorization/VLAN, and relay/scope availability. Disabling IPv6 can remove otherwise usable connectivity. |
| Static IP, duplicate address, or stale lease is wrong after a network change | Local configuration and conflict events can be observed; the intended addressing plan is external. | Confirm expected DHCP/static configuration against the subnet design. DHCP renewal or address changes can interrupt traffic. |
| Default gateway or expected route is absent or points to another interface | The route table is **endpoint-proven**. VPNs, IPv6, split routing, and deliberate isolation can be valid. | Evaluate the selected path for the intended destination and address family. A single adapter's default route is not a universal connectivity verdict. |
| ICMP ping fails | **Indicated** reachability limitation only. ICMP filtering, captive access, routing, or destination policy can explain it. | Compare a relevant service probe and routes. Ping failure alone does not establish that the gateway or Internet is down. |
| DNS servers are missing, unreachable, or give an unexpected answer | Configured resolvers are local facts. A failed query can reflect split DNS, VPN/NRPT policy, filtering, or missing records. | Use a test name with a known expected answer and compare resolver selection and DNS policy. A public resolver may not resolve internal zones or honor a split-DNS design. |
| Captive portal, quarantine, proxy, or restricted ACL blocks applications | Endpoint symptoms are **indicated**. Browser/proxy state and NAC authorization need separate checks. | Confirm the intended network role and application path. Access to a public site is not a universal authentication test. |
| IP/DNS works, but domain or application access fails | Successful probes prove only their destination, protocol, address family, context, and time. | Check the application, proxy, VPN, identity, and destination policy. Retain the distinction between 802.1X authorization and application authorization. |

## Validation scenarios

These scenarios help evaluate diagnostic accuracy in different environments; they are not a list of completed tests. Fixtures validate interpretation and output, not a real EAP handshake. Use bounded, synthetic, non-secret records and consult the [test results](../tests/test-results.md) for verified coverage.

| Scenario | Required invariant |
| --- | --- |
| Localized rendered messages share the same provider-specific numeric reason | Findings do not change with language; unknown codes remain unknown. |
| Old failure, later success, and a currently connected interface | History remains available, but the failure is not labeled the current connection state. |
| Events from two physical interfaces, a VPN, and an unmapped event | No cross-interface diagnosis; unmapped evidence remains unassigned. |
| Log is empty, disabled, missing, denied, truncated, or timed out | Each collection state stays distinct and visible. |
| Windows Wi-Fi/location query returns access denied | Report the limitation, not missing WLAN hardware or missing profiles. |
| Wired-only, Wi-Fi-only, and disconnected unused media | Unused services and adapters do not create false active-link failures. |
| `EapHost` is stopped with a demand-start configuration | No definitive authentication failure from that fact alone. |
| CurrentUser metadata comes from an administrator or SYSTEM, not the affected user | Report the collection identity and unobserved user context. |
| Certificate is expired, future-dated, has wrong EKU, lacks a private key, or has unknown key access | Keep each fact distinct; `HasPrivateKey` does not establish usable authentication. |
| Missing versus unconstrained EKU, issuer filters, and several eligible certificates | Avoid a universal EKU rule and avoid inventing the selected certificate. |
| PEAP-EAP-TLS, PEAP-MSCHAPv2, TTLS non-EAP phase 2, and TEAP chained inner methods | Preserve outer/inner scope and report unparsed extensions. |
| TEAP SHA-256 root pin, TLS/PEAP SHA-1 root pin, and an issuer-selection pin | Compare only the same algorithm and role; unsupported hash evaluation remains a limitation, not a missing-root verdict. |
| XML namespaces, missing optional defaults, malformed input, and nested unrelated `Type` elements | Missing defaults and unrelated `Type` elements do not establish disabled settings or active methods. |
| Credential Guard is configured, running, unavailable, or unknown on different builds | Separate intent from effective state; issue only method-relevant compatibility guidance. |
| GPO/MDM-owned profile differs from a local profile | Remediation targets the deployed configuration source; local edits can be overwritten. |
| IPv4 APIPA with usable IPv6, split VPN routes, or ICMP blocked | Avoid declaring all connectivity or 802.1X broken. |
| Certificate chain/revocation collection is offline, skipped, or unreachable | Unknown revocation does not become valid, revoked, or a proposed bypass. |
| Profile, event, and certificate text contains JSON/control metacharacters | Text/JSON output preserves data without executing it. |
| Output contains credential-like XML fields or untrusted diagnostic strings | No private key, password, profile `keyMaterial`, EAP user data, or shared secret is retained; diagnostic text does not become a command. |
| RADIUS timeout, rejection, wrong VLAN, or CoA symptom appears only at the endpoint | Preserve infrastructure uncertainty and give a useful correlation request. |
| One collector fails while the others succeed | Useful evidence is preserved, and the partial failure remains visible rather than implying complete coverage. |

Environment-specific validation still matters: standard and elevated collection, constrained-language or application-control limits, native XML/event shapes across builds and languages, actual user/machine certificate context, safe output handling, and wired/wireless collection without disrupting an active link. Method-specific end-to-end outcomes require correlated endpoint and RADIUS logs; synthetic fixtures do not establish those outcomes.

## Escalation package

Useful correlation details for a support request include:

1. Record the affected interface, SSID or wired switch-port context if known, OS build, authentication mode, and outer/inner method.
2. Record the failure time with time zone, capture time, and whether the failure still occurs. Include a success comparison if available.
3. Include the provider/channel/event ID, structured native reason code, and scoped collection limitations.
4. Include only needed certificate metadata: store/context, thumbprint, issuer, validity, relevant EKU, and mapping identity. Treat SAN/UPN and thumbprints as identifying data.
5. Ask for the matching authenticator and RADIUS/NAC session, policy, rejection, certificate/mapping result, and applied authorization attributes. For NPS, ask for the corresponding 6272/6273 event when available.

Passwords, private keys, profile key material, and RADIUS shared secrets are not needed for this package; including them exposes authentication secrets. Full exports can contain such data. SSIDs, MAC/IP addresses, certificate subjects, device names, and event messages can identify people and infrastructure. A report is not automatically anonymized.

## Official references

Use these references for method- and version-specific behavior. Check applicability to your Windows and RADIUS versions before making changes.

- [Advanced troubleshooting 802.1X authentication](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/802-1x-authentication-issues-troubleshooting): Correlate client events with NPS accept/reject and matched-policy evidence.
- [Configure EAP profiles and settings in Windows](https://learn.microsoft.com/en-us/windows-server/networking/technologies/extensible-authentication-protocol/configure-eap-profiles): Inspect the effective profile XML and method-specific settings; not all settings appear in the UI.
- [Certificate requirements for EAP-TLS and PEAP with EAP-TLS](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/certificate-requirements-eap-tls-peap): Check certificate purpose, identity, trust, and selection requirements on both sides.
- [Credential Guard considerations and known issues](https://learn.microsoft.com/en-us/windows/security/identity-protection/credential-guard/considerations-known-issues): Account for Windows upgrade behavior and MSCHAPv2/SSO compatibility without disabling Credential Guard.
- [The `netsh wlan` command](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-wlan): Distinguish metadata inspection from `key=clear` exports, which expose key material.
- [The `netsh lan` command](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-lan): Distinguish wired profile authentication mode and SSO settings from wireless settings.
- [EAP for network access in Windows](https://learn.microsoft.com/en-us/windows-server/networking/technologies/extensible-authentication-protocol/network-access): Distinguish outer and inner methods, client/server support, certificate selection filters, and version-specific behavior.
- [EAP changes in Windows 11](https://learn.microsoft.com/en-us/windows-server/networking/technologies/extensible-authentication-protocol/windows-11-changes): Check changed trust behavior, build-specific server-name case matching, and TLS defaults against the actual server version.
- [Changes to Wi-Fi API access and location](https://learn.microsoft.com/en-us/windows/win32/nativewifi/wi-fi-access-location-changes): Access denials and consent prompts affect which Wi-Fi metadata is available.
- [The `WlanReasonCodeToString` API](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/nf-wlanapi-wlanreasoncodetostring): A WLAN reason value has its own native namespace; its description is supplemental text.
- [The `ONEX_REASON_CODE` enumeration](https://learn.microsoft.com/en-us/windows/win32/api/dot1x/ne-dot1x-onex_reason_code): Distinguish user context, UI, profile validity, infrastructure nonresponse, and generic EAP-module errors. See Microsoft's [`dot1x.h`](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/dot1x.h) and [`l2cmn.h`](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/l2cmn.h) headers for numeric constants; those constants alone do not establish an event field's namespace.
- [The `CertGetCertificateChain` API](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain): Chain building and revocation require distinct cache-only flags; CurrentUser and LocalMachine use different chain-engine contexts.
- [RFC 5176: RADIUS dynamic authorization](https://www.rfc-editor.org/rfc/rfc5176.html): Correlate CoA/disconnect requests, NAS session identification, and ACK/NAK results on the infrastructure side.
- [KB5014754: Certificate-based authentication changes on Windows domain controllers](https://support.microsoft.com/en-us/servicing/os/windows-server/2022/05/kb5014754-certificate-based-authentication-changes-on-windows-domain-controllers): Check strong mapping, update-dependent enforcement, and KDC audit events on the domain controller.
